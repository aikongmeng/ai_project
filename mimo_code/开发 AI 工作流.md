开发 AI 工作流,本质上是把"一次大模型调用"升级成**可重复、有分支、能调用工具、能人工介入的流水线**。下面按从设计到落地的顺序讲一遍。

## 一、先选路线:三条路差别很大

| 路线 | 代表工具 | 适合场景 | 上手成本 |
|---|---|---|---|
| **无代码编排** | Dify、Coze、n8n、Make | 业务人员搭内部工具、快速验证想法 | 半天能跑通 |
| **代码框架** | LangChain、LlamaIndex、LangGraph、CrewAI | 需要复杂分支、自定义逻辑、要进生产系统 | 数天到数周 |
| **裸 API 手写** | 直接调大模型 HTTP 接口 | 流程短(2–3 步)、追求可控和低成本 | 最灵活也最费事 |

经验之谈:**先用无代码画出流程验证效果,再用代码重写关键链路**。直接上手写框架,很容易在没想清楚业务逻辑时就陷入调试。

## 二、通用开发步骤

**1. 拆解任务,而不是直接写 Prompt**
把人做这件事的步骤写下来。比如"处理客户邮件"是:读邮件 → 分类(咨询/投诉/退订) → 提取关键信息 → 查知识库 → 生成回复 → 人工确认 → 发送。每一步都是一个节点。

**2. 画出流程图,标出三类关键点**
- **分支点**:什么条件走哪条路(如意图分类结果)
- **失败点**:调用超时、输出格式不对、检索不到内容时怎么办(重试 / 兜底话术 / 转人工)
- **人工卡点**:高风险动作(发邮件、改数据、花钱)前必须留人工确认

**3. 为每个节点单独写 Prompt 并固化输出格式**
一个节点只做一件事。要求模型返回 JSON 或结构化字段(如 `{"intent": "...", "urgency": 1-5}`),这样下游节点才能可靠消费。结构化输出靠 schema 约束比靠"请返回 JSON"的自然语言指令稳定得多。

**4. 接工具(RAG / Function Calling)**
- 需要企业私有知识 → 做 RAG:文档切块 → 向量化 → 检索 → 塞进上下文
- 需要查数据库、调接口、算东西 → Function Calling,把工具描述给模型,让它决定何时调用

**5. 加护栏**
输入侧过滤敏感内容和注入攻击;输出侧校验格式、检查幻觉、做内容合规。用户提供的文本永远不要直接当指令用。

**6. 建评估集,再谈优化**
准备 30–50 条带标准答案的测试用例(覆盖常见 + 边界 + 故意刁难),每次改 Prompt 都跑一遍对比。没有评估集的迭代全凭感觉,改好一条改坏三条。

**7. 上线后看日志和成本**
记录每次的输入、输出、耗时、token 花费。很多工作流的成本大头不是模型,而是反复重试和冗长的上下文。

## 三、一个最小可跑的例子

以"会议纪要自动化"为例,流程是:`音频 → 转写 → 提炼纪要 → 提取待办 → 发到群里`。用 LangGraph 风格的伪代码表达编排逻辑:

```python
from langgraph.graph import StateGraph

def transcribe(state):        # 调用 ASR 接口
    state["text"] = asr(state["audio"])
    return state

def summarize(state):         # LLM 节点 1:提炼纪要
    state["minutes"] = llm(
        f"把会议转写整理成纪要,分'结论/分歧/背景':\n{state['text']}"
    )
    return state

def extract_tasks(state):     # LLM 节点 2:结构化输出
    state["tasks"] = llm_json(  # 强制 schema,保证下游可用
        "从纪要中提取待办,字段:负责人、事项、截止日期",
        schema={"tasks": [{"owner": "str", "task": "str", "due": "date"}]},
        input=state["minutes"],
    )
    return state

def notify(state):            # 人工卡点 + 外部动作
    if human_approve(state["minutes"]):
        send_to_group(state["minutes"], state["tasks"])
    return state

g = StateGraph()
for node in [transcribe, summarize, extract_tasks, notify]:
    g.add_node(node)
app = g.compile()   # 按顺序连线即可
```

换成 Dify 这类工具,这四步就是画布上四个节点拖线连起来,逻辑完全一样。

## 四、几个常见的坑

- **一个 Prompt 想干五件事** → 输出质量全面下滑。拆节点,每个节点职责单一。
- **没有兜底** → 模型输出格式偶发错误会导致整条流水线崩溃,务必做解析失败重试和默认值。
- **上下文无限膨胀** → 长对话要加摘要压缩或滑动窗口,否则又贵又慢。
- **跳过人工确认直接执行动作** → 上线后第一次幻觉就是事故。
- **只测"正常情况"** → 测试集里一定要有空输入、乱码、恶意指令、用户骂人这些刁钻样本。
